Agents and orchestration

Can this run end to end without someone driving it?

Asked by: Whoever gets paged when it goes wrong
The shape of it What we hear → what it becomes
What we hear

“Let’s get agents doing this end to end.”

What it becomes

Agents with named roles and scoped tool access, state that survives a crash, a retry path that does not loop forever, and a human approval before anything writes.

What the work actually is Five things, in order
  1. 01Name the roles, and give each the smallest tool access that still does the job.
  2. 02Design the state: what has to survive a crash, what has to be safe to run twice.
  3. 03Write the failure paths — retries that stop, fallbacks that degrade, and a dead end that pages a human.
  4. 04Put approval exactly where money, data or reputation changes hands, and nowhere else.
  5. 05Evaluate the whole run rather than the model, because that is what fails.
How it usually goes A composite, not a single client
It starts here
“Let’s get agents doing this end to end.”
Head of operations, logistics
  1. Week 1We map the process as it is actually performed rather than as documented. Eleven steps: three are a person deciding, the rest are someone copying between two systems. Only the copying should be automated. The deciding is the job.
  2. Week 2We write down what being wrong costs at each step. One can be retried for free; one sends an email a customer will read. That difference is the whole architecture.
  3. Weeks 3–5Four agents with named roles and scoped credentials. State in a durable store, so a crash resumes rather than restarts. Retries with a ceiling, and a dead end that pages a person instead of looping.
  4. Week 6Approval sits in front of the one step that writes to a customer; everything upstream runs unattended. The run is evaluated end to end, because that is what fails — the individual model calls were fine all along.
  5. Week 7Shadow mode on real volume. It stops twice, on cases nobody had described. Both become handled paths rather than surprises.
  6. Week 8Live for one region, with the pager pointing at a real person.
What we need from you The engagement stalls without these
  • Credentials for the real systemsSandbox access hides rate limits, timeouts and the record that has been broken since 2019 — which is the run that will fail.
  • The person who runs it todayA few hours a week. They know which of the eleven steps is the one that actually goes wrong.
  • A decision on what runs unattendedWhere a mistake is recoverable and where it is not. We will bring the question; someone senior has to answer it.
  • Somewhere for it to pageAn on-call route that exists. An agent that fails silently is worse than the manual process it replaced.
What usually goes wrong And what we do about it

Everything is one large agent.

Each role gets a name and the smallest tool access that still does the job. A failure then has a location, and a fix has a scope.

Retries loop until the invoice arrives.

Every retry has a ceiling and a fallback, and the dead end is a person rather than another attempt.

The prototype worked; the run does not.

Evaluation is written for the whole run, including the resume-after-crash path. Individual calls passing tells you very little.

Approval was put everywhere, so nobody reads it.

Approval sits only where money, data or reputation changes hands. Confirmation fatigue is a security failure with extra steps.

The shape of an engagement Typical timings; yours is scoped first
Weeks 1–2

Map and cost

The process as performed, and what a mistake costs at each step. The second half is the one people skip.

Weeks 3–5

Build the run

Roles, scoped tools, durable state, retries with ceilings, fallbacks that degrade rather than stop.

Weeks 6–7

Shadow

Real volume, no writes. We watch where it stops, and turn each stop into a handled path.

Week 8 onward

Live, then hand over

One team or region first, with the pager pointing somewhere real and a runbook that names the failure modes.

Questions we get asked Before the first call ends
How autonomous can this actually be?

More than most teams expect for retrieval and assembly; less than most vendors imply for anything that writes. The honest answer is per step rather than per system, and working it out is most of week one.

Which framework do you use?

Whichever survives your constraints. We have shipped on several and have no loyalty to any of them. The architecture — roles, state, failure paths — outlasts the framework, and is the part worth arguing about.

What happens when a model provider changes something?

The run is evaluated against a fixed set, so a regression arrives as a number rather than as a support ticket. Changing a model becomes a planned change with evidence attached.

Can we start with one step rather than the whole process?

Usually the right move. One step running unattended, with the pager wired up, teaches you more in a fortnight than a full pipeline sitting in shadow mode for a quarter.

We already have a prototype that half works.

Bring it. Reading what broke is faster than starting again, and the place it breaks is almost always the state handling rather than the model.
